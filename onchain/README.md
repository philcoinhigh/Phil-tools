# Phil on Solana

`first.phil` is a Phil program compiled by `philc`, Phil's own compiler, and run inside Solana's virtual machine.

```
component main provides U32 {
    let answer = 42
    return answer
}
```

## How it gets there

1. **Phil's compiler emits LLVM.** `emit.ts` runs the WebAssembly build of `philc` (see [`philc/`](../philc)) on `first.phil`. The LLVM it writes is kept as `first.philc.ll`, untouched.
2. **Two adjustments for Solana.** The lines naming a desktop target are dropped, and `main` is renamed `phil_main` so Solana's own entry point can call it. Nothing else changes.
3. **A small entry point.** `entry.c` is the only code that is not Phil: Solana calls `entrypoint`, which calls `phil_main` and writes what it returned to the transaction log.
4. **Solana's toolchain builds the program.** `build.sh` compiles both with Solana's clang and links them with the layout in `sbf.ld`. The result is `phil_first.so`, about 2 KB.
5. **It is called.** `invoke.mjs` sends one transaction to the program and reads the log.

`.github/workflows/onchain.yml` does all of this, first on a local test validator and then on devnet. `deployment.json` records what happened: the program address, the transaction, and the log.

## What this is and is not

- It is real: Phil source, Phil's compiler, Solana's virtual machine.
- It is tiny. Phil's compiler handles a `main` that returns a number today, so that is what the program does. It holds no tokens and takes no input.
- It is on **devnet**, Solana's public test network. Devnet is reset from time to time and its SOL has no value.
- The devnet wallet that deploys it is generated by the workflow and kept in the repository's Actions cache. It is never committed. It is a devnet-only key.

As Phil's compiler accepts more of the language, more of Phil can go on chain through the same steps.

## Every night

`onchain-nightly.yml` runs on main at 06:23 UTC and starts `onchain.yml` on the `onchain` branch.
That run:

1. compiles `first.phil` with the newest build of Phil's compiler (`docs/playground/philc.wasm`, rebuilt nightly from Phil's latest commit);
2. builds the Solana program and runs it on a local test validator;
3. deploys it to devnet again if the program's bytes changed or devnet was reset;
4. calls it, and also makes the wallet-free call the website's button makes;
5. writes `deployment.json`, appends to `history.json`, rebuilds the site and commits to main.

**Do not delete the `onchain` branch.** The devnet wallet is kept in the Actions cache in that
branch's scope, and GitHub drops a cache that has not been read for seven days; the nightly run
is what keeps it alive. A run that cannot read the wallet never makes a second one: it checks
what it can without a key and records that the paid call was skipped. A run started on the
`onchain` branch uses the workflow file from that branch, so a change to `onchain.yml` must be
on both branches.

## The button on the website

`site/src/solana-call.ts` builds an unsigned transaction by hand and asks a devnet node to
simulate it (`simulateTransaction` with `sigVerify: false`). The node executes the program
against the current chain state and returns the log; nothing is recorded, so no wallet is
needed. The tests check the hand-built bytes against `@solana/web3.js`.
